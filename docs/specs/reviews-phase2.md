# Reviews of the phase-2 specs (dashboard-invoices, manual-orders, dev-health)

## money-security

### blockers

- STALE PREMISE IN ALL THREE SPECS: discounts IS in the tree. C:\dev\calanthe\src\collections\Discounts.ts, src\migrations\20261004_202611_discounts.ts (registered in index.ts), src\backend\payments\coupon-claims.ts, redeem.ts and src\backend\data\discounts.ts all exist, and orderIntegrity.ts validateOrderTotals already enforces `couponDiscountFils === discountFils` plus sale/snapshot rules. Manual-orders must be rewritten against that code (not 'feature-detect later'), its migration is generated AFTER 20261004_202611_discounts, and the health spec's 'schema probe will fail on discounts' note is obsolete.
- DASHBOARD COUNTS REFUNDED MONEY AND NEVER SAYS SO. The webhook (src\app\(payload)\api\webhooks\stripe\route.ts) only writes a '⚠ STRIPE: ... refunded' note on charge.refunded; nothing ever sets REFUNDED / PARTIALLY_REFUNDED. The spec's three footnotes render only when those statuses have count > 0, so they can never appear, while the card is labelled 'Money received. Cancelled and refunded orders are not counted.' That sentence is false today. Fix before shipping the label: either (a) record refunds in the signed webhook under PAYMENT_PROVIDER_CONTEXT (charge.refunded -> refundedFils additive column + PAID -> PARTIALLY_REFUNDED/REFUNDED; allowed by the hard rule because it is the signed webhook), or (b) at minimum count orders in the period whose internalNotes contain the '⚠ STRIPE:' refund/dispute marker and show an always-on footnote 'n orders have a refund or dispute in Stripe; this figure does not subtract them', and change the basis sentence.
- FAKE PAID SALE WITHOUT THE OFFLINE AUDIT TRAIL (ordering dependency between two specs). Today guardPaymentStatus guards only UPDATE and Orders has `create: isAdmin` with paymentStatus field `create: isStaffField`, so an owner session (or a stolen owner cookie) can POST /api/orders with paymentStatus PAID and any reconciling totals. The dashboard spec's issueMissingInvoiceNumbers then hands that row a real CAL-INV number with no method, reference or recorder, and it shows up in Paid sales and the CSV. The manual-orders 'CREATE must be PENDING' rule in guardPaymentStatus therefore has to ship BEFORE (or with) the dashboard/invoices feature, not after, and issueMissingInvoiceNumbers must additionally refuse rows that have neither stripePaymentIntentId nor an offline paymentMethod unless they were created before a hard-coded cutoff date (the numbering launch), and must list the order numbers it numbered in the activity entry.
- OFFLINE PAID PATH MUST FAIL CLOSED ON STRIPE UNCERTAINTY. applyOfflinePayment step 3 only defines 'cancel refused -> retrieve'. If cancel OR retrieve throws (network, 5xx, rate limit) the spec is silent and an implementer will 'continue'. Rule to add: proceed to the PAID write only when there is no stored intent after the re-read, or Stripe positively answered that the intent is `canceled`; every other outcome (throw, timeout, unknown status, requires_capture) restores payLinkExpiresAt and returns payment-in-progress. Also the role check must be on a user row re-read from the database inside applyOfflinePayment (id -> role === 'admin', status active), not on the `actor` object the caller passes.
- VERDICT RULE IS SPECIFIED BUT NOT WIRED. The new 'settled && paymentMethod !== card -> flag' rule in verdict.ts does nothing unless paid.ts passes paymentMethod into the OrderFacts object it builds (paid.ts lines 154-162 pass only id, totalFils, paymentStatus, orderNumber, stripePaymentIntentId). Without that line a card payment landing on a hand-paid order is answered 'already-paid' and, worse, when the hand-paid order has no invoice yet (crash window) the webhook's recovering branch would claim the invoice and send card emails. Add the field at the call site and a paid.test.ts case for 'offline PAID, no invoice, card intent succeeds -> flagged, no claimInvoice call'.
- DUPLICATE-SUBMIT GUARD BURNS ITSELF ON FAILURE. createManualOrder consumes LIMITS.manualOrderOnce (step 4) before parsing, pricing and the shownTotalFils check (steps 5-8). Any validation error, priceChanged or productUnavailable then makes the retry answer 'This order was already created' for 10 minutes although nothing exists, and staff will create it again with a new requestId after reloading, or worse believe it exists. Move the once-guard to immediately before payload.create and release it (or use a fresh requestId from the server response) when create throws; better, make it real idempotency by storing requestId in the order (additive nullable unique column in the same migration) and returning the existing order on replay.
- MANUAL ORDER + DISCOUNT CODE COLLIDES WITH THE BUILT CLAIM/HOLD MACHINERY. In the tree a code is reserved by every non-cancelled order carrying it (data/discounts.ts claimWhere has no source filter), stale-order release only sweeps source 'web-checkout-card' (coupon-claims.ts line 164), and paid.ts writes LATE_DISCOUNT_NOTE for any discounted order paid more than DISCOUNT_HOLD_MINUTES (60) after creation. A manual order with a code and a 7-day link therefore (1) holds a claim for 7 days and for ever once the link expires uncancelled, so staff can exhaust a 'first 20' code with unpaid drafts; (2) gets a '⚠ DISCOUNT CHECK' flag on essentially every link payment; (3) those flags then light up the health page's orderFlags row. Decide and specify: either no codes on link-mode manual orders in v1 (codes only with 'paid outside', redeemed immediately), or give coded manual orders the 60-minute expiry and include MANUAL_SOURCE in the sweep. createManualOrder must also call the real admit/second-look functions in coupon-claims.ts, not 'the same live-claim counting the discounts build ends up with'.
- HEALTH: DEVELOPER IDENTITY CAN BE MINTED BY THE OWNER WHEN NO ACCOUNT HOLDS THE EMAIL. The Users hook in the spec only blocks changing an existing developer account and 'setting another user's email' on update. Users.access.create is isAdmin, so if any DEVELOPER_EMAILS entry has no user row yet (first deploy, typo, preview database copy, account deleted) the owner creates a staff account with that email in Team or /cms and gets Health. Rule: beforeChange on CREATE and UPDATE refuses any write that results in a developer email unless req.user is that developer or there is no req.user (seed script/CLI); the developer account is bootstrapped only by script. Also treat the grant as (email in list) AND (user id in an optional DEVELOPER_USER_IDS list when set) so a re-created row with the same email is not enough.

### improvements

- State honestly that 'staff see no aggregated money' and 'CSV is owner-only' are UI courtesies, not controls: Orders.access.read is isStaffOrOwnerOf, so any staff session can GET /api/orders?limit=...&depth=0 (or GraphQL) and read every order's totalFils, customerEmail and customerPhone, and the invoices list lets them page through all totals. The 404 on /admin/invoices/export stops nothing. If the owner really wants staff blind to takings or unable to bulk-export customers, that is a separate decision (field read access on totals / a REST page-size cap for staff); otherwise drop the claim from docs/SECURITY.md wording. Put it to the owner as a question.
- CSV export is the one-click exfiltration path for a stolen OWNER cookie (20,000 rows of name, email, phone, silently, GET, no trace). Add: recordActivity on every export (actor, filters, row count, marked notable), a throttle (e.g. 10 per hour per user), a default requirement of a date range (no 'all time' in one file), and consider dropping phone from the default columns. Keep no-store and noindex.
- resendInvoice is throttled per order only (5/hour). A compromised staff session can loop over every paid order and mail every customer. Add a per-user limit (e.g. 30/hour) alongside the per-order one; same for recordOfflinePayment (no throttle specified at all; add e.g. 30/day per owner) and lower manualOrder from 60/hour, since each link-mode creation sends a Calanthe-branded email with staff-typed text to an arbitrary address.
- Dashboard window query: add `paymentStatus in [PAID, REFUNDED, PARTIALLY_REFUNDED]` to the where clause (PENDING/FAILED rows are never used by summariseSales, bestSellers or the footnotes; awaitingPayment uses the separate openOrders query). Without it abandoned checkouts, which any visitor can create, eat the 5,000-row limit. And sort '-createdAt', not 'createdAt': when truncated the spec's ascending sort throws away the NEWEST rows, i.e. the current period. Better still for the totals: one SQL SUM/COUNT grouped by Dubai day through drizzle, as invoice-number.ts already does raw SQL.
- Staff can defeat the owner-only 'Amount off' by typing a custom line ('Amber Hour', AED 2) instead of the catalogue product. Either accept it (it equals today's payment-request power) and say so, or make custom lines owner-only / flag in the activity entry and the owner 'paid' email whenever an order contains a custom line, with its description and price.
- createdBy must be `create: serverOnlyField` (not immutableAfterCreate, whose create is isStaffField), otherwise an owner REST create can attribute an order to another staff member. Same for salesChannel/manualDiscountFils being writable on REST create: harmless only because validateBespokeLines' manual branch requires payTokenHash, which REST cannot set. Add an explicit test 'owner REST POST with source admin-manual is refused' so that accidental protection cannot be lost, and add the simplest explicit rule: source admin-manual or admin-quote on create requires a server context flag.
- guardPaymentRecord: 'data.paymentMethod defined while neither context flag is present -> 403' must be 'defined AND different from originalDoc', or any overrideAccess update that passes a full document back (scripts, future actions) breaks. Also add a DB CHECK that an offline payment_method implies payment_status in (PAID, REFUNDED, PARTIALLY_REFUNDED) and paid_at IS NOT NULL.
- Fraud visibility for 'paid outside': the control against a fake or pocketed cash sale is out-of-band notice, so make it mandatory, not incidental: the owner email on every hand-recorded payment must go out even when there is no customer email and when alreadyDelivered is set; show a permanent dashboard line 'Recorded by hand this period: n orders, AED x' (owner) and include paid-then-cancelled orders with who cancelled them. Mark 'PAID order moved to CANCELLED' as a notable activity entry, since that move removes the sale from Paid sales.
- Owner-only recording has a practical failure mode: staff who take cash at the door will be given the owner's login. Ask the owner now; if staff must record cash, allow it for staff with the same trail plus the owner email, rather than driving credential sharing.
- issueMissingInvoiceNumbers uses year = invoiceYear(paidAt ?? createdAt), which can issue new numbers into a previous (closed) year's series long after later numbers of the next year exist. paid.ts does the same on a late replay, so it is consistent, but have the accountant confirm; the safer alternative is to number backfills in the year of issue and print the original payment date on the invoice.
- Health redact(): pattern-matching misses UPSTASH_REDIS_REST_TOKEN, BLOB_READ_WRITE_TOKEN, PAYLOAD_SECRET, HEALTH_CHECK_TOKEN, the Sentry DSN key and database hostnames. Redact by VALUE as well: build the list of every secret env value at module load and replace any occurrence in an outgoing string; keep the regexes as a second net. Extend the 'never print a secret' test to all of them.
- Health public (token) report: toPublicReport still renders messages with {error} vars (dbDown, schemaBroken, stripeKeyRejected, checkCrashed), which then live in a third-party uptime monitor's logs. For via 'monitor' render the code and status only, or a fixed sentence without vars. Drop `commit` and `region` from the public shape unless needed.
- Webhook heartbeat: recordWebhookSignatureFailure is an unauthenticated write. Anyone can POST a junk stripe-signature header in a loop and make each request perform an awaited Redis read-modify-write (up to 400 ms each) against the same Upstash database that backs the rate limiter, burning its quota. Use a single non-awaited INCR + EXPIRE (or sample to one write per minute via SET NX), never read-modify-write, and do not await it on the 400 path.
- Health 404 parity needs an automated test, not only a manual check: one test that renders /admin/health and /admin/zzz as owner, staff and anonymous and asserts identical status, headers of interest and body; and one for /api/health vs /api/zzz for GET/HEAD/POST/OPTIONS. Also assert the RSC payload of a normal admin page for the owner contains neither '/admin/health' nor the nav strings, and that no public file (robots.ts, sitemap, docs/ADMIN.md, OWNER_TODO.md, en.ts/ar.ts) names it. The new main-dictionary key team.errors.protected should not say 'developer'; use 'This account is protected and can't be changed here.'
- Health: cookie-authenticated /api/health returns order numbers and masked emails as JSON; set the response for developer sessions to also require the same-origin `Sec-Fetch-Site` (or simply serve the full report only on the page and let the endpoint always return the public shape). Simpler and removes one surface.
- Health copy conflicts with the manual-orders feature once it lands: paidNoInvoiceBroken ('resend the payment_intent.succeeded event') is impossible for a hand-paid order (the fix is pressing Record payment again / the owner's backfill button), payLinks and stalePending must use PAY_LINK_SOURCES, and orderFlags should distinguish '⚠ DISCOUNT CHECK' from payment warnings. Add a health row 'hand-recorded payments in the last 7 days' so the developer sees the volume.
- csvCell: also guard cells whose first non-space character is = + - @ (leading spaces are trimmed by some spreadsheets) and cells starting with LF. Apply the guard to every text column including order source labels, and never to the numeric columns.
- Invoice resend goes to the order's snapshot email with a /pay/[token] link rebuilt from payTokenSalt: confirm the pay page for a PAID order shows only the invoice allow-list (src/backend/data/pay.ts) once manual orders add lines, and never the payment reference, recorder, internal notes or discount reason. Add that as a test on PayRequestView.
- Customer linking in manual orders: staff-picked `customerId` plants an order (with staff-typed lines) into a real customer's account page. Keep it, but record the link in the activity entry and do not let staff obtain account ids for customers they did not find through an order snapshot (the action should re-derive the id from the matched order, not trust the id sent by the browser).

### improvements

- WHATSAPP ORDER - TAP COUNT. Spec B's own count ('10 steps') leaves out real taps. Honest count for the best case (repeat customer, one catalogue product, link): Orders tab (1) > Create order (2) > Add product (3) > [type 3 letters] > product row (4) > size chip if not Standard (5) > Add to order (6) > customer search [type 4 digits] > tap match (7) > Use last address (8) > date field + pick day + Done (9-11) > time chip (12) > Take payment (13) > 'Send payment link' card (14) > Create order and send link (15) > lands on the order page > Send on WhatsApp (16) > WhatsApp opens > Send (17).
