# Reviews of the two specs

## money-security

### blockers

- DISCOUNTS — usage limit, once-per-customer and expiry are not enforceable as specified (customer can apply a code many times and after expiry). The code is checked only when the PENDING order is created; usage is counted only at PAID; a Stripe PaymentIntent never expires. So a customer (or script, 8 orders/hour per IP under LIMITS.checkout) can create many PENDING orders with a 'first 20 customers' or once-per-customer code, keep the client secrets, and pay them all later — every one is 'honoured and flagged'. Same for an automatic sale: order created during the sale can be paid weeks after it ended. Smallest fix: (a) store stripePaymentIntentId on the order at intent creation in startCardCheckout (the quote spec adds the column); (b) in priceCheckout, under `pg_advisory_xact_lock(discount id)` or an equivalent single SQL statement, count live claims = redeemed orders + PENDING orders with that couponDiscount created in the last N minutes (e.g. 60), and for once-per-customer count the same for the email; refuse when claims >= limit; (c) lazily sweep: whenever a code is quoted/used, cancel the PaymentIntent (stripe.paymentIntents.cancel) of PENDING coded/sale orders older than N minutes and set them CANCELLED, so a stale discounted order can no longer be paid. Add unit tests for the claim count and a test that a stale order's intent is cancelled.
- QUOTE-PAY — a second successful intent for an already-PAID order is silently swallowed (double charge with no flag). C:\dev\calanthe\src\backend\payments\verdict.ts returns 'already-paid' purely on order.paymentStatus === 'PAID' and never compares the intent id. With a 7-day link this becomes reachable: if ensureOrderPaymentIntent creates an intent but the write of stripePaymentIntentId fails, after ~24h the idempotency key is forgotten and a second intent is created; two tabs can then each pay. Fix: (1) ensureOrderPaymentIntent must persist the intent id BEFORE returning the client secret, and on a failed write cancel the just-created intent and return FAILED; (2) extend paymentVerdict OrderFacts with stripePaymentIntentId: when the order has a stored id and intent.id differs -> 'flag' (reason 'second payment for a paid order — refund in Stripe') instead of already-paid/mark-paid; add tests. This same check also closes 'webhook marks the wrong order paid' across environments that share one Stripe test account but different databases (metadata.orderId 12 exists in both DBs): require intent.id === order.stripePaymentIntentId (and metadata.orderNumber === order.orderNumber) before mark-paid, for web checkout too.
- QUOTE-PAY — cancel race lets a cancelled request be paid, then 'Confirm again' produces a second payable order (customer can pay twice). cancelPaymentRequest cancels the Stripe intent FIRST and sets CANCELLED second; in between, startQuotePayment sees state 'awaiting' + stored intent 'canceled' and creates a fresh replacement intent (key order-{id}-r-{old}) whose client secret the customer now holds for a cancelled order. Fix the ordering: write fulfilmentStatus CANCELLED first (startQuotePayment then refuses), re-read stripePaymentIntentId, then cancel the intent; if Stripe refuses because it is processing/succeeded, revert the fulfilment status to its previous value and return actions.quote.paymentInProgress. Also remove the automatic 'canceled -> create a fresh intent' branch from the customer path; only resendPaymentRequest (staff) should clear a cancelled intent id.
- BOTH — the new code is NOT safe to deploy before its migration, and nothing runs migrations automatically. package.json build is plain `next build` and payload.config.ts has push:false with no prodMigrations. Payload selects every configured column, so the moment code with the new Orders fields (enquiry_id, pay_token_hash, invoice_number, coupon_discount_id, orders_items.sale_id, payload_locked_documents_rels.discounts_id …) serves traffic against the old schema, EVERY orders read/write fails: checkout order creation, the Stripe webhook findByID (payments captured but never marked PAID until Stripe retries succeed), admin orders. The specs say 'additive, run migration first' but do not make it enforceable. Required: state in both specs that the order is strictly `pnpm migrate` against production -> verify -> deploy code, add it to the release checklist/docs, and never merge the collection changes to main (auto-deploy) before the migration has been applied. Migration-before-code is safe (old code ignores extra nullable/defaulted columns; enum ADD VALUE is harmless).
- DISCOUNTS — quoteCheckout is a public customer-membership oracle. It accepts any customerEmail and answers CODE_ALREADY_USED when that email has a redeemed order with the code, so anyone holding a public once-per-customer code (e.g. a welcome code) can test whether arbitrary email addresses are Calanthe customers (12 probes per 10 min per IP, indefinitely). Fix: do not take an email in quoteCheckout at all; run the once-per-customer check only in startCardCheckout (already throttled at 8/hour and requiring a full valid order), and return the refusal there.
- DISCOUNTS — the code throttle as specified will break checkout for honest customers who hold a valid code. The cart re-quotes via quoteCheckout on every item/quantity change and on hydration, and every such call spends LIMITS.discountCode (12 per 10 min, per network address — shared offices/NAT share it). Once exhausted the quote returns RATE_LIMITED, the cart shows discount 0, shownTotalFils no longer matches or the pay buttons stay disabled, and the customer cannot complete payment with a code they were shown. Fix: spend the bucket only on REFUSED 'inactive' answers (unknown/draft/expired code), never on a successful re-quote of an accepted code; add a throttle test for that.
- EXISTING LEAK made worse by both specs — Orders.internalNotes has no field-level read rule and Orders.read is isStaffOrOwnerOf('customer'), with Payload REST and GraphQL mounted at src/app/(payload)/api. A signed-in customer can GET /api/orders/{id} for their own order and read internalNotes and assignedStaff. Both specs now write sensitive text there ('PAID AFTER CANCELLATION — refund in Stripe', '⚠ DISCOUNT CHECK: code X redeemed past its limit', existing '⚠ PAYMENT CHECK'), and the discounts spec adds discountSnapshot containing the INTERNAL discount title. Fix in the same migration-free code change: `access: { read: isStaffField }` on internalNotes, assignedStaff, discountSnapshot, couponDiscount, items.sale, enquiry, payLinkExpiresAt, stripePaymentIntentId; and drop `title` from discountSnapshot.sales/coupon or keep it staff-read only.

### improvements

- QUOTE-PAY: enforce quote rules in the collection, not only in actions. Add to validateBespokeLines: source 'admin-quote' requires discountFils === 0, couponDiscountFils 0/empty, couponCode empty, deliveryFeeFils === 0, exactly one item, quantity 1 (guarantees no discount can ever land on a quote). Add a beforeChange hook: an admin-quote order with paymentStatus !== PAID may only change fulfilmentStatus to CANCELLED, and a CANCELLED unpaid quote cannot be un-cancelled — today Orders.update is isStaff, so a REST PATCH or /cms edit bypasses the rule that lives only in updateOrderFulfilment (and un-cancelling would revive the pay link).
- QUOTE-PAY: crash-recovery branch ('PAID but no invoiceNumber -> claim and send emails') will also fire for every historical PAID order if an old event is ever resent from the Stripe dashboard, re-sending customer emails for old orders. Guard it: only fall through when the order has stripePaymentIntentId === intent.id AND (paidAt is null or within the last 72h, Stripe's retry horizon); otherwise claim an invoice number silently without emails. Add a test.
- QUOTE-PAY: claimInvoice SQL needs explicit casts or Postgres cannot infer parameter types through drizzle: `$year::int`, `'CAL-INV-' || $year::text`, `$paidAt::timestamptz`, `$rate::numeric`. Also add `AND payment_status = 'PAID'` to the `target` CTE so an invoice number can never be minted for an unpaid order by a future caller. Keep it outside any Payload transaction (autocommit) as specified; add the concurrent-claim test against a real scratch Postgres, not only a fake.
- QUOTE-PAY: merge the paid path order explicitly: mark PAID (+stripePaymentIntentId) -> redeemCoupon (own try/catch) -> claimInvoice (winner gate) -> emails. The recovery fall-through must also run redeemCoupon (it is idempotent via coupon_redeemed_at), otherwise a crash between PAID and redeem is never healed.
- QUOTE-PAY: account auto-linking by matching a verified users row to the enquiry's free-typed email puts the enquirer's delivery address and phone into another person's account history when the email was mistyped or malicious. Link only when enquiry.customer is already set (enquiry made while signed in); otherwise guest.
- QUOTE-PAY: token hygiene — return_url `${origin}/pay/${token}` hands the token to Stripe/3-DS redirect pages (acceptable, state it); Sentry (@sentry/nextjs is installed) records request URL and transaction name, not only breadcrumbs — scrub `/pay/<token>` in beforeSend/beforeSendTransaction and in any tunnel; Vercel access logs will contain it (accept, document). Paid-state page shows name/email/items to any link holder forever: consider showing the invoice by link for 30 days after payment, then 'see your email'.
- QUOTE-PAY: startQuotePayment on an 'expired' link is refused, but an already-issued client secret stays payable indefinitely and the order's totals never expire. When resend/expiry logic runs and the order is expired + unpaid for more than e.g. 24h, cancel the stored intent so an old tab cannot pay a weeks-old quote; resend then creates a fresh one.
- QUOTE-PAY: the hand-added partial unique index means 'reinstating' a cancelled-but-paid order fails with a unique violation if 'Confirm again' already created a live one. Document the human procedure (refund the late payment in Stripe; never reinstate) and make the owner email say exactly that instead of 'refund or reinstate'.
- QUOTE-PAY: escape every enquiry-derived string (contactName, address, description, customerNote) in HTML bodies and strip CR/LF from anything placed in a subject line; add a test with `<script>` and a newline in the name. Use formatFils for amounts so 'AED 650.50' never prints as 'AED 650.5'.
- QUOTE-PAY: confirmEnquiryQuote steps 7 and 8 are two writes; if the enquiry update fails the order exists and the email is not sent. Send the email whenever the order was created, and treat the enquiry status update as non-fatal (logged), so no payable order exists without the customer or staff knowing.
- DISCOUNTS: saleUnitFils can return 0 for a very cheap arrangement (e.g. 150 fils at 90% floors to 0, which passes the 'safe integer >= 0 and strictly lower' rule). Require result >= 100 else return unchanged; add the test.
- DISCOUNTS: say explicitly that src/backend/data/discounts.ts reads with overrideAccess: true (products.ts relies on the Local API default; Discounts.read is isAdmin, so an `overrideAccess: false` read with no user returns nothing and no sale or code would ever apply), and that only the mapped allow-list fields leave the module. Admin actions keep user + overrideAccess false.
- DISCOUNTS: timesUsed is `required` with `access.create: () => false` — verify Payload still applies defaultValue 0 when create access strips the field; otherwise drop `required` and rely on the column default. Also add validateOrderTotals rule: discountFils === couponDiscountFils (not just >=), so no unexplained order-level discount can be written.
- DISCOUNTS: startCardCheckout should store the order's stripePaymentIntentId at creation and put couponCode only in metadata (never amounts). Add test: tampered shownTotalFils lower/higher than server total -> PRICE_CHANGED and payload.create not called.
- DISCOUNTS: findCoupon should enforce length <= 24 and the code pattern BEFORE querying, and 'exhausted'/'min_spend' answers confirm a code exists — acceptable, but keep them behind the same failed-attempt throttle.
- DISCOUNTS: invoice (quote spec buildInvoice) for a web order with a sale/coupon must print the Discount row and reconcile sum(lines) + delivery − discount === total; add that fixture to invoice.test.ts.
- BOTH: package manager is pnpm (pnpm-lock.yaml); the discounts spec's `npm run …` commands should be `pnpm …`.
- BOTH: webhook only handles payment_intent.succeeded. Add logging/flagging for payment_intent.canceled and charge.refunded/charge.dispute.created at least as an internalNotes line, since both features now create situations ('paid after cancellation', over-limit code) where a human refunds in Stripe and the order would otherwise still read PAID with a valid invoice.

### conflictsBetweenSpecs

- Migrations: both specs generate a migration with `payload migrate:create`, whose .json snapshot is cumulative. They must be created sequentially on one branch (quote_pay_link first, then discounts); generating them in parallel branches yields a second snapshot that drops or duplicates the other's columns. Each also registers in src/migrations/index.ts.
- src/backend/payments/paid.ts: both rewrite applySucceededIntent and OrderDoc. Quote spec makes claimInvoice the single-winner gate and changes the 'already-paid' early return; discounts spec inserts redeemCoupon 'immediately after the PAID update' and says the already-paid branch must not call it. Needs one merged sequence (PAID -> redeemCoupon -> claimInvoice -> emails; recovery path runs redeem + claim).
- src/backend/payload/hooks/orderIntegrity.ts: quote spec adds validateBespokeLines/guardInvoiceNumber and totals 'unchanged'; discounts spec extends validateOrderTotals with compareAt/coupon rules. Both create a NEW orderIntegrity.test.ts. Also quote orders must be explicitly excluded from discounts (discountFils 0, no couponCode, no items.sale) — neither spec states it in the hook.
- Email templates: quote spec makes shell() bilingual and adds 'payment-received' with a full invoice for quote orders only; discounts spec edits the English-only order-confirmation totals. Decide once whether order-confirmation becomes bilingual (Orders.locale is added by the quote spec but startCardCheckout does not set it) and whether web orders show their invoice number; PricedOrder in email/types.ts is edited by both.
- src/components/commerce/CheckoutForm.tsx: quote spec extracts APPEARANCE / loader / Express options into stripe-shared.ts 'with no visual change'; discounts spec changes Elements `amount` (line 272) and many price lines in the same file. Do the extraction first, then the discount edits.
- src/backend/actions/admin.ts: quote spec moves ActionResult/failure/actorOf into admin-shared.ts; discounts spec extends failure() uniqueField ('slug' | 'code') in admin.ts and adds four actions there. Apply the move first and extend in the shared file.
- Admin order detail page (orders/[orderNumber]/page.tsx) and account order page are edited by both (awaiting-payment notice, invoice line, bespoke-line no-link vs struck prices, sale badge, discount row). OrderOps prop changes vs Orders listSearchableFields change (couponCode).
- Throttle LIMITS and dictionary/admin i18n files are extended by both (payView/payStart/payResend vs discountCode; pay.* / server.pay.* vs discount.* / server.checkout.*) — no key clashes, but one PR at a time to keep en/ar parity tests green.
- Activity log: quote spec logs with area 'orders'; discounts spec uses area 'other' to avoid touching the activity_log enum. Fine, but the owner's activity screen filter will show discount changes under 'other' — confirm or add the enum value in the discounts migration.
- Tooling wording: quote spec uses pnpm, discounts spec uses npm (repo is pnpm).
- Invoice numbering applies to ALL paid orders (quote spec) — discounted web orders therefore need the invoice builder to understand compareAt/sale labels and the coupon row from the discounts spec.

## admin-ux

### blockers

- QUOTE-PAY / dashboard treats an unpaid payment request as a real order (verified in src/backend/domain/dashboard.ts and src/backend/data/dashboard.ts). isPlaced = fulfilmentStatus !== CANCELLED, so the moment staff confirm a quote: (a) its amount is added to 'Revenue (placed orders)' and to the daily chart and top products, (b) it is counted in 'N new orders waiting to be confirmed' (newOrders = open orders with status NEW) although the florist can do nothing with it, (c) it appears in 'Today's deliveries' if the date is today, and (d) once the delivery date passes it becomes an 'overdue delivery' forever, because an expired link leaves the order NEW until someone cancels it. Risk: a florist prepares flowers from 'Today's deliveries' for an order nobody paid. The spec only says 'verify admin-pulse.ts and dashboard.ts' in edge cases. It must be a concrete rule in one place: add `isAwaitingQuote(order) = source === 'admin-quote' && paymentStatus not in PAID/REFUNDED/PARTIALLY_REFUNDED` to backend/domain/dashboard.ts and exclude those orders from isPlaced-based revenue, newOrders, todaysDeliveries, overdue (also in the /admin/orders `attention=overdue` query) and openOrders-by-status; unit-test each.
- QUOTE-PAY / the shop is never told in the admin that a quote was paid. The bell (src/backend/data/admin-pulse.ts) is keyed on orders.createdAt, and the spec auto-moves a paid quote NEW -> CONFIRMED, so it also skips the dashboard 'new orders' queue. Result as specified: confirming a quote rings the bell as a 'new order' (wrong moment), and the payment itself is silent everywhere except one email to EMAIL_REPLY_TO. The user asked explicitly: 'when he pay we will get another confirmation'. Required: pulse must skip admin-quote orders at creation and add a third item kind 'payment' driven by orders.paidAt (title '{orderNumber} paid', detail '{name} · AED X', link to the order); plus a dashboard Needs-attention row 'N paid bespoke orders to start' (admin-quote, PAID, fulfilment CONFIRMED) so it is still visible the next morning.
- QUOTE-PAY / on a phone the primary action is at the bottom of the page. The spec puts the Payment card 'at the TOP of the right-hand column', but in src/app/(admin)/admin/(panel)/enquiries/[id]/page.tsx the right column is the second child of a single-column grid below lg, so at 390px 'Confirm & request payment' sits under the message, the request details, the customer card and the conversation card. The florist works on a phone. Fix in the spec: render the QuotePayment card ABOVE the grid (full width, before 'What they asked') at all widths, or pass the primary button through PageHeader's existing `actions` prop; same for the unpaid-quote Notice + buttons on the order page.
- QUOTE-PAY / a wrong customer email cannot be corrected as specified. The spec's remedy is 'cancel, then create the corrected enquiry by hand', but /admin has no create-enquiry screen (only enquiries/page.tsx and [id]/page.tsx exist), so the owner would need /cms, which docs/ADMIN.md says she never needs. Since the email is written onto the NEW order at confirm time (Orders.customerEmail is only immutable after create), the dialog must include an editable 'Send to' email field prefilled from the enquiry, validated server-side; the payment email, Stripe receipt_email and invoice then all go to the corrected address. Without it a typo in the enquiry form means the money request and the invoice go to a stranger or nowhere.
- BOTH SPECS edit the same money path and cannot be built in parallel. src/backend/payments/paid.ts (applySucceededIntent + OrderDoc), src/collections/Orders.ts, src/backend/payload/hooks/orderIntegrity.ts, src/backend/email/templates.ts, CheckoutForm.tsx and the admin order detail page are changed by both. Unmerged, the paid path is ambiguous: quote-pay returns 'already-paid' early when claimInvoice says claimedNow=false, discounts calls redeemCoupon 'immediately after the PAID update and before the emails'. The merged order must be written down once: verdict -> PAID update -> redeemCoupon (own exactly-once claim, own try/catch, runs for winner and for crash-recovery retries) -> claimInvoice gate -> winner only: emails. Otherwise a crash between PAID and redeem never counts the code, or the redeem is skipped by the early return.
- BOTH SPECS / two Payload migrations generated from the same snapshot will corrupt the migration chain. `payload migrate:create` diffs against the previous .json snapshot; quote_pay_link and discounts both ALTER orders. If built on separate branches each snapshot omits the other's columns and the second one applied will try to re-create or drop columns. They must be created strictly one after the other on the same branch (quote-pay first), and the discounts spec's 'expected SQL' re-checked after the first lands. Also the specs disagree on the tool: the repo has pnpm-lock.yaml, so every `npm run ...` in the discounts spec must be `pnpm ...`.
- DISCOUNTS / one mistaken save changes every price on the live store with no confirmation. The form defaults to Active=on, start=now, Applies to=All products, and Save publishes immediately (revalidateStorefront). Typing 50 instead of 5, or choosing Percentage instead of Fixed, sells the whole catalogue at half price until someone notices, and orders already paid are honoured. Required before Save for any discount whose resulting status is Active: a ConfirmDialog (existing primitive) stating the consequence in numbers computed on the server, e.g. 'This changes the price of 42 products now. Lowest price becomes AED 96 (Peony Cloud, was AED 480).' for a sale, and 'Anyone with code EID10 gets 10% off from now.' for a code; no dialog for Draft or Scheduled. Also default Active to OFF on create for 'All products' sales.
